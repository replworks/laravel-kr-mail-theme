# Laravel 이메일 테마 패키지

**한 줄 요약**: 서비스 코드에는 비즈니스만 두려고, 한국 서비스용 라라벨 이메일 테마(로고·서비스명·푸터·unsubscribe 버튼 등)를 블로그 테마처럼 별도 패키지로 만들고, workbench + Mailpit에서 보고·발송·테스트한 뒤 서비스에서 불러다 쓰는 본인용 유틸리티. 공개 레포로 올릴 예정.

**결정 준비도**: 판단 가능 — 본인 전용 유틸리티로 범위가 정해졌고, 동기·첫 사용처(wifinote.net)·비용·수익(무료)이 답해짐. 기존 대안 조사만 비어 있음.

---

## 1. 발단

- wifinote 이메일 작업 맥락에서 AI와 workflow를 이야기하던 중, 사용자가 "라라벨 이메일 테마 패키지를 별도로 만들어 workbench에서 웹으로 보고 발송 테스트하고, 됐다 하면 패키지로 불러와 쓰는 게 Workflow로 가장 좋지 않냐"고 제안.
- AI가 처음엔 반대(앱 안에서 해결)했고, 사용자가 이유를 밝히자 AI가 입장을 바꿈.
- 이메일은 보내는 건 간단해도 테스트가 굉장히 까다로움. 보는 디바이스마다 테스트해야 하는데 그게 서비스 안에 들어가는 게 이상하다는 것이 사용자의 이유.
- 회사에서 서비스를 만들 때도 꽤 괴로웠음 (한국법에 따라 만들어야 하는 스킨 테마 같은 것).
- 마지막에 사용자가 "REPL Works 스타일로 개발해 보자"고 함. ("REPL Works 스타일"이 구체적으로 뭔지는 이 대화에서 논의 안 됨)

## 2. 문제와 대상 사용자

- 이메일 테마와 그 테스트가 서비스 코드 안에 들어가는 게 싫음. 서비스 코드에는 비즈니스만 있었으면 함.
- 이메일 테스트가 꽤 빡셈. Mailpit과 강하게 연결될 필요가 있음.
- 서비스를 다수 만들 예정인데, 그때마다 라라벨 본체에 이메일 테마를 넣을 방법이 패키지 말고는 마땅치 않음.
- 대상 사용자: **사용자 본인뿐**. 내 서비스들에만 쓸 유틸리티.
- 사설 저장소가 있으면 거기 올려야 할 프로젝트지만, 키 관리가 무서워서 공개 레포로 올리려 함.

## 3. 아이디어

사용자가 말한 것:

- 이메일 테마 패키지를 따로 만든다. workbench에서 웹으로 보고, 발송하고, 테스트한다. 확정되면 서비스에서 패키지를 불러와 쓴다.
- Mailpit과 강하게 연결.
- 한국 서비스에 맞는 형태로 여러 가지 테마를 만들어 둠. 블로그 테마처럼.
- 들어가는 요소: 로고, 서비스 이름, 푸터, unsubscribe 버튼 등.
- 감당(유지 부담)을 적게 하려고 패키지로 만드는 것. 안 만들면 감당이 안 됨.
- 첫 적용은 wifinote.net.

사용자가 "오케이"로 전반 수용한 AI 제안 (세부 항목별 확인은 없음):

- 경계: 패키지는 껍데기(헤더·푸터·버튼·수신거부 영역·색/폰트 토큰·테마 여러 벌), 서비스는 본문 문구와 `MailMessage` 내용. 브랜드 정보는 config 한 파일로 전달.
- 패키지 workbench 미리보기는 샘플 본문 fixture로 껍데기만 검증.
- Testbench workbench에 Mailpit 컨테이너를 같이 띄우고, 테마별 발송 → Mailpit API로 검사, 테마 × 샘플 본문 스냅샷 테스트.
- Laravel 연결은 `mail.markdown.paths` / `mail.markdown.theme`로 패키지 뷰 우선 사용, 서비스는 `composer require` + config 몇 줄.
- 처음엔 wifinote 하나에만 적용해 슬롯/토큰 인터페이스가 안정된 뒤 두 번째 테마를 만듦.

**사용자가 위임해 AI가 정리한 것** ("내 결정이 필요 없는 것 같으니 네가 해결해줘"). 사용자가 개별 확인한 내용은 아님:

1. 한국 조건 정리
   - 법적 근거는 정보통신망법 제50조이고 KISA 안내서는 그 해석서. "KISA 가이드가 대신한다"는 안내서가 해석 기준이라는 뜻으로 정리.
   - 위반 시 제재는 검색에서 과태료(제76조)로만 확인됨. "형법 쪽"은 확인 못 함.
   - 패키지 README에 근거 조항과 참조한 안내서 개정 시점(2026-03)을 적어둠.
2. 광고 표기 경계
   - 패키지: 정보성/광고성 레이아웃 분리. 광고성 푸터에는 발신자 정보와 수신거부 링크 슬롯이 필수이고, 비면 렌더가 실패. 정보성 레이아웃에는 광고 슬롯을 두지 않음.
   - 서비스: `(광고)` 제목 접두어, 수신거부 처리(로그인 없이), 사전동의 수집, 야간 발송 제한.
   - workbench(Mailpit) 테스트: fixture 메일의 제목 접두어와 푸터 필수 항목 누락 검사.
3. 인터페이스가 깨질 때
   - wifinote 하나로 슬롯/토큰을 안정시킨 뒤 두 번째 테마를 만든다.
   - 안정되기 전엔 0.x 버전으로 두고 breaking change 허용. 서비스는 버전을 고정해 쓰고, 슬롯/토큰이 바뀌면 CHANGELOG에 적음.
   - 깨지면 패키지와 사용 중인 본인 서비스를 같이 고쳐서 배포 (첫 서비스를 같이 수정·배포하는 dogfooding 방식과 같은 흐름).

## 4. 기존 대안

- 앱 안에서 해결(AI 첫 답변): `vendor:publish --tag=laravel-mail`로 테마 CSS/header/footer 수정, `APP_ENV=local` 전용 미리보기 라우트, Mailpit(로컬) + Resend 실발송 테스트(`RUN_LIVE_MAIL_TEST`).
- 사용자: 이게 되는 건 알지만 서비스 코드 안에 들어가는 게 싫음.
- 사용자가 찾아본 결과: 라라벨 메일 테마 패키지는 못 찾음. 한국엔 외부 메일 템플릿도 없고 "그냥 발송만 있음".

## 5. 증거

- **존재 증거**: 사용자 진술뿐 — 라라벨 메일 테마 패키지를 못 찾았고, 한국엔 외부 메일 템플릿 없이 발송 서비스만 있음. (조사 방법·범위는 대화에 없음)
- **수요 증거**: 사용자 본인의 필요. 회사에서 서비스를 만들 때 겪은 괴로움(한국법에 맞춘 스킨 테마). 다른 사람의 불만이나 지불 사례는 없음.
- **사용자의 추측 (태그 없음)**: 한국 서비스들의 이메일이 말도 안 되게 오는 건 현실적으로 만들기 어려워서일 수도 있음.
- **반증/한계**: 아무도 신경을 안 쓰기 때문에 돈을 내고 쓰지는 않음. 이후 AI의 첫 답변 반대 논거(아래 6번)도 있었으나 철회됨.
- **상업화 가능성 (사용자 의견, 검증 없음)**: 상업적으로 본다면 한국에 진출하는 외국 회사에게 제공하는 게 나을 수도 있음. 한국은 이메일 관련 법이 깐깐한 게 몇 개 있음.

## 6. 반론과 의문

| 반론/의문                                                                        | 상태                                                                        |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 재사용처가 없는데 패키지로 빼면 abstraction without use (AGENTS.md DESIGN_RULES) | 해소 — 다수 서비스 전제로 쓸 곳이 정해져 있다고 정리                        |
| 새 패키지는 `TECH_STACK` 변경 절차가 필요                                        | 해소 — 사람이 결정하고 문서에 한 줄 올리면 되는 절차                        |

| 인터페이스(슬롯·토큰)가 두 번째 서비스에서 깨질 수 있음                          | 사용자 위임으로 AI가 정리 — 3번의 3항 (0.x 버전, 버전 고정, 같이 고쳐 배포) |
| 사설 저장소 대신 공개 레포로 올리는 것                                           | 사용자가 결정 — 키 관리가 무서워서                                          |

## 7. 성공 조건(가정)과 한국 조건

대화에서 "fatal"로 표시된 항목은 없음. 아래는 모두 검증 안 됨.

사용자가 말한 것:

- 이메일 발송 쪽에는 따로 법규가 없고 KISA 가이드가 대신함. 문제가 발생했을 때 치고 들어오는 것이며 그건 형법 쪽. ("플랫폼 법규 의존"은 비즈니스 쪽 이야기로 구분)
- 한국에는 이메일 관련 법이 깐깐한 게 몇 개 있음. (위 항목과 어떻게 연결되는지는 논의 안 됨)

사용자가 "광고 표기 문제는 네가 생각해 봐야지"라고 AI에게 넘김. AI가 검색으로 확인한 것 [출처: KISA 안내서 개정(2026-03) 관련 보도와 발송 사업자 가이드 문서, 원문 직접 확인은 안 함]:

- 근거는 정보통신망법 제50조(영리목적 광고성 정보 전송 제한). KISA 안내서는 그 해석 기준. 위반 시 과태료 조항(제76조)이 있다고 사업자 가이드에 적혀 있음.
- 이메일은 제목 시작 부분에 `(광고)` 표기, 하단 푸터에 수신거부/동의 철회 방법 안내. 수신거부 비용은 수신자 부담 없어야 함.
- 광고성 정보 전송은 수신자의 명시적 사전동의가 필요하고, 오후 9시~다음날 오전 8시 전송 금지.
- 정보성 메시지(거래 안내 등)는 수신동의가 불필요하지만, 부수적으로 광고가 섞이면 전체가 광고성 정보로 간주된다고 채널톡 가이드에 적혀 있음.
- 앱 푸시 광고 수신거부 때 로그인/본인인증을 요구하면 수신거부 방해 행위라고 안내함.
- 쿠폰·마일리지 발급/소멸 안내도 광고성 정보로 보는 개정 해석이 있음.

AI가 처음 제시한 것 (출처 태그 없음):

- 광고성 메일은 `(광고)` 제목 표기, 수신거부 방법, 발신자 정보가 법적으로 필요(정보통신망법) → 트랜잭션용/광고용 푸터 구분
- 네이버/다음/카카오 웹메일이 CSS를 깐깐하게 먹음 → 테이블 기반 + 인라인 유지
- 폰트 스택: `Apple SD Gothic Neo`, `Malgun Gothic`, `Noto Sans KR`
- 다크모드, 모바일 폭(Gmail 앱, 네이버 앱) 대응

## 9. 논의 중 바뀐 점 / 기각된 방향

- 기각: "앱 안에서 해결, 별도 패키지는 비추천" (AI 첫 답변). wifinote 단일 서비스 기준 판단이었음.
- 바뀐 점: 사용자가 "서비스 코드엔 비즈니스만 + 다수 서비스 + 한국용 테마 여러 벌"을 밝히자 AI가 패키지 분리가 맞다고 번복.
- 범위 조정: 패키지는 전체 메일이 아니라 껍데기(layout)만, 본문은 서비스 몫.
- 배포 방식: 패키지만 만드는 게 아니라 첫 서비스(wifinote.net)도 같이 수정해서 배포. 이를 위한 버전이고 dogfooding이라고 함.
- 남은 질문 3개(한국 조건 2, 반증 1)는 사용자가 AI에게 정리를 맡김.
- 범위 확정: 본인 전용·무료 유틸리티. "너무 깊게 생각할 필요는 없다"고 함. 공개 레포로 올림.

## 10. 빠진 것과 미해결 질문

사용자가 답한 항목(발단, 대상 사용자, 기존 대안, 수요 증거, 누가 돈을 내는가, 플랫폼·법규 의존, 단위 경제, 첫 사용자)은 위 본문에 반영.

- 비어 있는 이유: 사용자도 모르고 중요하지 않다고 함. 상업적 목적의 패키지가 아니기 때문.
- 가장 그럴듯한 실패 이유: 사용자는 "실패할 일 없다, 우선 wifinote.net에 쓸 거니까"라고 답함.

남은 것: 없음. 한국 조건 2건과 반증 1건은 사용자가 "내 결정이 필요 없는 것 같다"며 AI에게 맡겼고, 정리 내용은 3번에 있음 (사용자 개별 확인 아님).
